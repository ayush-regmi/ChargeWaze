# Chargewise — Database Design

Status: **Draft (specification phase)** · Last updated: 2026-11-17

Postgres schema for the modular monolith. Owned by the backend only; the frontend never connects to the database directly. Managed with SQLAlchemy models and Alembic migrations under [`services/api/alembic/`](../services/api/alembic/).

## 1. Principles

- **Provenance on everything.** Rows that originate from an external provider record `source`, provider `recorded_at`, server `received_at`, and the raw unit. This applies to telemetry, charging stations, weather observations, and anything else fetched externally.
- **Simulated data is tagged.** Any row produced for the public demo carries `is_simulated = true`. Analytics and ML queries filter it out unless explicitly opted in.
- **Ownership is enforced.** Every user-owned table has a `user_id` foreign key. Every query the API performs scopes by `user_id` at the ORM layer.
- **Soft-delete where history matters.** Vehicles aren't hard-deleted on disconnect; they're flagged `connection_status = 'disconnected'` so historical trips still resolve.
- **UUID primary keys.** Generated by the database (`gen_random_uuid()` via `pgcrypto`).
- **UTC timestamps.** `timestamptz` everywhere; the app layer never stores naïve timestamps.
- **No cross-module joins hidden in migrations.** Each module owns its tables; cross-module reads go through service methods, not raw joins.

## 3. Tables

### 3.1 `profiles`

Supabase Auth owns identity; this table is Chargewise's profile extension and is keyed by Supabase's user ID.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | Equals Supabase `auth.users.id`. |
| `display_name` | `text` | Nullable. |
| `created_at` | `timestamptz` | Default `now()`. |

### 3.2 `user_preferences`

One-to-one with `profiles`. Created lazily on first write.

| Column | Type | Notes |
|---|---|---|
| `user_id` | `uuid` PK FK → `profiles.id` ON DELETE CASCADE | |
| `units` | `text` | `'imperial'` or `'metric'`. |
| `reserve_soc` | `numeric(4,3)` | 0..1. Default 0.15. |
| `preferred_charge_to` | `numeric(4,3)` | 0..1. Default 0.80. |
| `max_detour_minutes` | `int` | Default 20. |
| `preferred_networks` | `jsonb` | Array of operator names. |
| `primary_vehicle_id` | `uuid` FK → `vehicles.id` ON DELETE SET NULL | |

Constraints:
- `CHECK (reserve_soc BETWEEN 0 AND 1)` and same for `preferred_charge_to`.
- `CHECK (units IN ('imperial', 'metric'))`.

### 3.3 `vehicles`

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `user_id` | `uuid` FK → `profiles.id` ON DELETE CASCADE | |
| `smartcar_vehicle_id` | `text` | Nullable for simulated vehicles. |
| `smartcar_user_id` | `text` | Nullable for simulated vehicles. Smartcar V3 stores no per-user tokens; the application token + this ID are enough ([`smartcar-v3-notes.md`](smartcar-v3-notes.md)). |
| `smartcar_connection_id` | `text` | Nullable. Smartcar V3 connection ID, used by disconnect (`DELETE /v3/connections/{id}`). Cleared once Smartcar confirms the revocation; a `disconnected` row that still has one is a revocation still owed (Smartcar was unreachable at disconnect time). |
| `make` | `text` | Not null. |
| `model` | `text` | Not null. |
| `year` | `int` | Not null. |
| `connection_status` | `text` | `'connected'`, `'disconnected'`, `'pending'`. Default `'pending'`. |
| `supported_signals` | `jsonb` | Array of signal codes returned by Smartcar for this vehicle. Default `[]`. |
| `latest_state` | `jsonb` | Cached snapshot, see shape below. Written only by the webhook ingestor. `NULL` until the first event arrives. |
| `connected_at` | `timestamptz` | Nullable. |
| `disconnected_at` | `timestamptz` | Nullable. Set on disconnect, cleared on reconnect. |
| `is_simulated` | `boolean` | Default `false`. |

`latest_state` shape (phase2_plan.md D5):

```json
{
  "recorded_at": "2026-11-06T18:52:00Z",
  "received_at": "2026-11-06T18:52:08Z",
  "signals": {
    "soc": { "value": 72, "unit": "percent", "recorded_at": "2026-11-06T18:52:00Z" }
  }
}
```

- Keys under `signals` are Chargewise signal codes (the same ones as `supported_signals`).
- Each signal keeps its own provider `recorded_at` and only moves forward (out-of-order rule, D5).
- The top-level `recorded_at` is the max across signals; `received_at` is our clock for the newest delivery.
- Readers take the max of the top-level and per-signal `recorded_at` and treat anything malformed as "no data yet".

Constraints and indexes:
- `CHECK (connection_status IN ('connected', 'disconnected', 'pending'))`.
- `UNIQUE (user_id, smartcar_vehicle_id) WHERE smartcar_vehicle_id IS NOT NULL` — prevents duplicate connects of the same real vehicle. Reconnecting a disconnected vehicle reactivates its existing row.
- `INDEX (user_id, connection_status)`.

### 3.4 `vehicle_specs`

One-to-one with `vehicles`. Separated so vendor-provided and user-configured spec data can evolve without blocking the hot path of telemetry.

| Column | Type | Notes |
|---|---|---|
| `vehicle_id` | `uuid` PK FK → `vehicles.id` ON DELETE CASCADE | |
| `usable_capacity_kwh` | `numeric(6,2)` | User-editable; defaults seeded per make/model from a static catalog. `NULL` when unknown (never guessed). `CHECK (> 0)`. |
| `connectors` | `jsonb` | e.g. `["NACS", "J1772", "CCS1"]`. Default `[]`. |
| `charging_curve` | `jsonb` | Piecewise `[{soc, power_kw}, ...]`. Default `[]`. |

### 3.5 `vehicle_telemetry`

Append-only log of every signal reading.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `vehicle_id` | `uuid` FK → `vehicles.id` ON DELETE CASCADE | |
| `recorded_at` | `timestamptz` | Provider timestamp. |
| `received_at` | `timestamptz` | Server receive time. Default `now()`. |
| `source` | `text` | `'smartcar'`, `'manual'`, `'simulated'` (`CHECK`). |
| `source_event_id` | `text` | Smartcar event ID for deduplication; nullable for manual. |
| `signal_code` | `text` | e.g. `soc`, `odometer`, `range`, `charging_status`. |
| `value` | `numeric` | Raw numeric. For booleans use 0/1 and document in a code table. Nullable when the signal has no numeric value (kept in `raw_payload`). |
| `unit` | `text` | e.g. `percent`, `km`, `kwh`. Nullable. |
| `raw_payload` | `jsonb` | Full normalized signal entry for auditability: `{smartcar_code, outcome, error_code, text_value, retrieved_at, signal}`, where `signal` is the Smartcar entry as received. Errored and unmapped signals are stored too (with `value` `NULL`); unmapped ones keep Smartcar's code as `signal_code`. |
| `is_simulated` | `boolean` | Default `false`. |

Indexes:
- `UNIQUE (source, source_event_id, signal_code) WHERE source_event_id IS NOT NULL` — webhook deduplication at signal granularity.
- `INDEX (vehicle_id, signal_code, recorded_at DESC)` — hot path for "latest SoC".
- `INDEX (vehicle_id, recorded_at DESC)` — history scrolling.

### 3.6 `charging_stations`

Cached station records. Treated as a local cache of external data, not the source of truth. Global data with no `user_id`; RLS is enabled like every `public` table. Searches always go to the provider and **upsert** each result on `(provider, external_id)`, so a station's `id` stays the same across fetches and can be referenced by favorites and `planned_stops` ([phase3_plan.md](phase3_plan.md) D7). Nullable columns stay `NULL` when the provider doesn't give a value; nothing is guessed.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | Stable Chargewise ID. |
| `provider` | `text` | `'afdc'`, `'simulated'` (`CHECK`). AFDC includes NRCan's Canadian data, so there is no separate Canadian provider (phase 3 F0). |
| `external_id` | `text` | Provider's station ID. Not null. |
| `name` | `text` | Not null. |
| `operator` | `text` | Nullable. |
| `network` | `text` | Nullable. Provider network code (AFDC `ev_network`). |
| `street_address` | `text` | Nullable. |
| `city` | `text` | Nullable. |
| `region` | `text` | Nullable. State or province. |
| `postal_code` | `text` | Nullable. |
| `country` | `text` | Nullable. ISO 3166-1 alpha-2, e.g. `'US'`, `'CA'` (`CHECK ~ '^[A-Z]{2}$'`). |
| `lat` | `numeric(9,6)` | Not null. `CHECK (BETWEEN -90 AND 90)`. |
| `lon` | `numeric(9,6)` | Not null. `CHECK (BETWEEN -180 AND 180)`. |
| `connectors` | `jsonb` | `[{ type, count, power_kw }]`. `type` is `NACS`, `CCS1`, `J1772` or `CHAdeMO`; `count` and `power_kw` are `null` when the provider doesn't give them per connector (never derived from level totals). Default `[]`. |
| `access` | `text` | `'public'`, `'private'`, `'unknown'` (`CHECK`). Default `'unknown'`. |
| `access_detail` | `text` | Nullable. Provider access restriction detail (AFDC `access_detail_code`), shown as-is. |
| `status` | `text` | `'open'`, `'planned'`, `'temporarily_unavailable'`, `'unknown'` (`CHECK`). Default `'unknown'`. |
| `pricing_text` | `text` | Nullable. Provider pricing text (AFDC `ev_pricing`), shown as-is and never parsed. |
| `source_updated_at` | `timestamptz` | Nullable. Provider's own last-updated timestamp. |
| `fetched_at` | `timestamptz` | When we last fetched the row from the provider; drives the TTL refresh. Default `now()`. |
| `raw_payload` | `jsonb` | Not null. The provider record as received, for auditability and fields we don't map yet. |
| `is_simulated` | `boolean` | Default `false`. `CHECK (is_simulated = (provider = 'simulated'))`. |
| `created_at` | `timestamptz` | Default `now()`. |

Constraints and indexes:
- `UNIQUE (provider, external_id)` — the upsert target.
- `INDEX (lat, lon)` — upgradable to a PostGIS `GIST` index on `geography(Point)` when needed.

### 3.7 `planned_trips`

A trip the planner produced. The entire plan payload is stored in `plan_payload` so the UI can re-render without recomputing.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `user_id` | `uuid` FK → `profiles.id` ON DELETE CASCADE | |
| `vehicle_id` | `uuid` FK → `vehicles.id` ON DELETE CASCADE | |
| `origin` | `jsonb` | `{ lat, lon, label }`. |
| `destination` | `jsonb` | `{ lat, lon, label }`. |
| `status` | `text` | `'planned'`, `'completed'`, `'abandoned'`. |
| `plan_payload` | `jsonb` | The full `/routes/plan` response for reproducibility. |
| `model_version` | `text` | e.g. `'deterministic-v1'`. |
| `is_simulated` | `boolean` | Default `false`. |
| `created_at` | `timestamptz` | |

Index: `INDEX (user_id, created_at DESC)`.

### 3.8 `planned_stops`

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `trip_id` | `uuid` FK → `planned_trips.id` ON DELETE CASCADE | |
| `station_id` | `uuid` FK → `charging_stations.id` | Nullable if the station cache has been evicted. |
| `sequence` | `int` | |
| `arrival_soc` | `numeric(4,3)` | |
| `departure_soc` | `numeric(4,3)` | |
| `charging_minutes` | `int` | |

Index: `UNIQUE (trip_id, sequence)`.

### 3.9 `observed_trips`

A real-world trip, either inferred from telemetry or manually confirmed.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `user_id` | `uuid` FK → `profiles.id` ON DELETE CASCADE | |
| `vehicle_id` | `uuid` FK → `vehicles.id` ON DELETE CASCADE | |
| `start_time` | `timestamptz` | |
| `end_time` | `timestamptz` | |
| `distance_km` | `numeric(8,2)` | |
| `energy_kwh_estimated` | `numeric(8,3)` | |
| `energy_source` | `text` | `'soc_inferred'`, `'odometer_inferred'`, `'manual'`. |
| `quality_flag` | `text` | `'high'`, `'medium'`, `'low'`. |
| `is_simulated` | `boolean` | Default `false`. |

Index: `INDEX (vehicle_id, start_time DESC)`.

### 3.10 `prediction_results`

Pairs a prediction with an observation so the analytics module can compute error.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `planned_trip_id` | `uuid` FK → `planned_trips.id` ON DELETE CASCADE | |
| `observed_trip_id` | `uuid` FK → `observed_trips.id` ON DELETE SET NULL | Nullable until an observation is matched. |
| `model_version` | `text` | |
| `predicted_energy_kwh` | `numeric(8,3)` | |
| `observed_energy_kwh` | `numeric(8,3)` | Nullable. |
| `arrival_soc_error_points` | `numeric(5,2)` | Percentage points. Nullable until observed. |
| `created_at` | `timestamptz` | |

Index: `INDEX (model_version, created_at)`.

## 4. Provenance and unit discipline

- `source`, `recorded_at`, `received_at` live on every externally derived row.
- `vehicle_telemetry.raw_payload` keeps the normalized signal entry even after it has been projected into typed columns, so that a later schema migration can re-derive values without round-tripping to Smartcar.
- Units are stored raw. The API layer exposes units in field names (`range_km`, `odometer_km`); the frontend converts for display.

## 5. Simulated vs real data

The public demo depends on being able to seed convincing plans without touching real vehicles. Rules:

- Seeded rows land in the same tables with `is_simulated = true`.
- All default analytics, ML training, and `/api/v1/analytics/consumption` queries filter `is_simulated = false`.
- The seed script lives in `services/api/scripts/seed_demo.py` (to be created in Phase 6) and must never run against a database that contains real telemetry.

## 6. Location and privacy

- Location columns (`vehicles.latest_state.location`, `observed_trips` paths, `charging_stations.lat/lon`) are classified sensitive.
- Account deletion removes `profiles` and cascades to `user_preferences`, `vehicles` (and through them `vehicle_specs`, `vehicle_telemetry`, `planned_trips`, `planned_stops`, `observed_trips`, `prediction_results`).
- `charging_stations` is global cache data and is not removed on account deletion.
- Telemetry retention policy: keep 24 months by default; user-configurable in Phase 6. Rows older than retention are deleted by a nightly job (not yet scheduled).
- No raw lat/lon is included in Sentry breadcrumbs or logs. Coordinates are rounded to 2 decimal places in log output.

## 7. Migration policy

- Every schema change is a reviewed Alembic migration. No ad-hoc SQL in production.
- Migrations must be reversible, or explicitly document why they are not.
- CI runs `alembic upgrade head && alembic downgrade -1 && alembic upgrade head` against a disposable Postgres.
- Breaking column changes follow expand/contract: add the new column, backfill, switch readers, switch writers, drop the old column in a later migration.

## 8. When to add PostGIS

Not in the MVP. Adopt PostGIS when the first query that actually benefits from it appears — likely "find chargers within X km of a route polyline" if we start caching routes. Until then, provider APIs handle proximity.

## 9. Open database questions

- Partition `vehicle_telemetry` by month once row count makes `(vehicle_id, recorded_at DESC)` queries slow. Reassess after Phase 2 ships.
- Whether `observed_trips` needs a `path` column (LineString) or should stay with aggregate distance only until mobile tracking exists.
- Where to store weather observations tied to trips — a separate `trip_weather` table vs embedding in `observed_trips`. Decide in Phase 5.
