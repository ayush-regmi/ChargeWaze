# Chargewise — Database Design

Status: **Draft (specification phase)** · Last updated: 2026-11-19

Postgres schema for the modular monolith. Owned by the backend only; the frontend never connects to the database directly. Managed with SQLAlchemy models and Alembic migrations under [`services/api/alembic/`](../services/api/alembic/).

## 1. Principles

- **Provenance on everything.** Rows that originate from an external provider record `source`, provider `recorded_at`, server `received_at`, and the raw unit. This applies to telemetry, charging stations, weather observations, and anything else fetched externally.
- **Simulated data is tagged.** Any row produced for the public demo carries `is_simulated = true`. Analytics and ML queries filter it out unless explicitly opted in.
- **Ownership is enforced.** Every user-owned table has a `user_id` foreign key. Every query the API performs scopes by `user_id` at the ORM layer.
- **Soft-delete where history matters.** Vehicles aren't hard-deleted on disconnect; they're flagged `connection_status = 'disconnected'` so historical trips still resolve.
- **UUID primary keys.** Generated by the database (`gen_random_uuid()` via `pgcrypto`).
- **UTC timestamps.** `timestamptz` everywhere; the app layer never stores naïve timestamps.
- **No cross-module joins hidden in migrations.** Each module owns its tables; cross-module reads go through service methods, not raw joins.

## 3. Tables

### 3.1 `profiles`

Supabase Auth owns identity; this table is Chargewise's profile extension and is keyed by Supabase's user ID.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | Equals Supabase `auth.users.id`. |
| `display_name` | `text` | Nullable. |
| `created_at` | `timestamptz` | Default `now()`. |

### 3.2 `user_preferences`

One-to-one with `profiles`. Created lazily on first write.

| Column | Type | Notes |
|---|---|---|
| `user_id` | `uuid` PK FK → `profiles.id` ON DELETE CASCADE | |
| `units` | `text` | `'imperial'` or `'metric'`. |
| `reserve_soc` | `numeric(4,3)` | 0..1. Default 0.15. |
| `preferred_charge_to` | `numeric(4,3)` | 0..1. Default 0.80. |
| `max_detour_minutes` | `int` | Default 20. |
| `preferred_networks` | `jsonb` | Array of operator names. |
| `primary_vehicle_id` | `uuid` FK → `vehicles.id` ON DELETE SET NULL | |

Constraints:
- `CHECK (reserve_soc BETWEEN 0 AND 1)` and same for `preferred_charge_to`.
- `CHECK (units IN ('imperial', 'metric'))`.

### 3.3 `vehicles`

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `user_id` | `uuid` FK → `profiles.id` ON DELETE CASCADE | |
| `smartcar_vehicle_id` | `text` | Nullable for simulated vehicles. |
| `smartcar_user_id` | `text` | Nullable for simulated vehicles. Smartcar V3 stores no per-user tokens; the application token + this ID are enough ([`smartcar-v3-notes.md`](smartcar-v3-notes.md)). |
| `smartcar_connection_id` | `text` | Nullable. Smartcar V3 connection ID, used by disconnect (`DELETE /v3/connections/{id}`). Cleared once Smartcar confirms the revocation; a `disconnected` row that still has one is a revocation still owed (Smartcar was unreachable at disconnect time). |
| `make` | `text` | Not null. |
| `model` | `text` | Not null. |
| `year` | `int` | Not null. |
| `connection_status` | `text` | `'connected'`, `'disconnected'`, `'pending'`. Default `'pending'`. |
| `supported_signals` | `jsonb` | Array of signal codes returned by Smartcar for this vehicle. Default `[]`. |
| `latest_state` | `jsonb` | Cached snapshot, see shape below. Written only by the webhook ingestor. `NULL` until the first event arrives. |
| `connected_at` | `timestamptz` | Nullable. |
| `disconnected_at` | `timestamptz` | Nullable. Set on disconnect, cleared on reconnect. |
| `is_simulated` | `boolean` | Default `false`. |

`latest_state` shape (phase2_plan.md D5):

```json
{
  "recorded_at": "2026-11-06T18:52:00Z",
  "received_at": "2026-11-06T18:52:08Z",
  "signals": {
    "soc": { "value": 72, "unit": "percent", "recorded_at": "2026-11-06T18:52:00Z" }
  }
}
```

- Keys under `signals` are Chargewise signal codes (the same ones as `supported_signals`).
- Each signal keeps its own provider `recorded_at` and only moves forward (out-of-order rule, D5).
- The top-level `recorded_at` is the max across signals; `received_at` is our clock for the newest delivery.
- Readers take the max of the top-level and per-signal `recorded_at` and treat anything malformed as "no data yet".

Constraints and indexes:
- `CHECK (connection_status IN ('connected', 'disconnected', 'pending'))`.
- `UNIQUE (user_id, smartcar_vehicle_id) WHERE smartcar_vehicle_id IS NOT NULL` — prevents duplicate connects of the same real vehicle. Reconnecting a disconnected vehicle reactivates its existing row.
- `INDEX (user_id, connection_status)`.

### 3.4 `vehicle_specs`

One-to-one with `vehicles`. Separated so vendor-provided and user-configured spec data can evolve without blocking the hot path of telemetry.

| Column | Type | Notes |
|---|---|---|
| `vehicle_id` | `uuid` PK FK → `vehicles.id` ON DELETE CASCADE | |
| `usable_capacity_kwh` | `numeric(6,2)` | User-editable; defaults seeded per make/model from a static catalog. `NULL` when unknown (never guessed). `CHECK (> 0)`. |
| `connectors` | `jsonb` | e.g. `["NACS", "J1772", "CCS1"]`. Default `[]`. |
| `charging_curve` | `jsonb` | Piecewise `[{soc, power_kw}, ...]`. Default `[]`. |
| `baseline_kwh_per_km` | `numeric(5,3)` | User-entered consumption baseline (phase4_plan F8). `NULL` means "use the catalog value" ([`phase4_plan.md`](phase4_plan.md) D14); never copied from the catalog, so a non-null value is always the user's. `CHECK (> 0 AND <= 1)`. |

### 3.5 `vehicle_telemetry`

Append-only log of every signal reading.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `vehicle_id` | `uuid` FK → `vehicles.id` ON DELETE CASCADE | |
| `recorded_at` | `timestamptz` | Provider timestamp. |
| `received_at` | `timestamptz` | Server receive time. Default `now()`. |
| `source` | `text` | `'smartcar'`, `'manual'`, `'simulated'` (`CHECK`). |
| `source_event_id` | `text` | Smartcar event ID for deduplication; nullable for manual. Rows from an on-demand refresh (ADR 0010) use `poll:<vehicle_id>:<recorded_at ISO>`, since a REST read has no event ID. The vehicle is part of the ID because the unique index below doesn't include `vehicle_id`. |
| `signal_code` | `text` | e.g. `soc`, `odometer`, `range`, `charging_status`. |
| `value` | `numeric` | Raw numeric. For booleans use 0/1 and document in a code table. Nullable when the signal has no numeric value (kept in `raw_payload`). |
| `unit` | `text` | e.g. `percent`, `km`, `kwh`. Nullable. |
| `raw_payload` | `jsonb` | Full normalized signal entry for auditability: `{smartcar_code, outcome, error_code, text_value, retrieved_at, signal}`, where `signal` is the Smartcar entry as received. Errored and unmapped signals are stored too (with `value` `NULL`); unmapped ones keep Smartcar's code as `signal_code`. |
| `is_simulated` | `boolean` | Default `false`. |

Indexes:
- `UNIQUE (source, source_event_id, signal_code) WHERE source_event_id IS NOT NULL` — webhook deduplication at signal granularity. For refresh rows it also makes refreshing the same OEM reading twice a no-op.
- `INDEX (vehicle_id, signal_code, recorded_at DESC)` — hot path for "latest SoC". Also serves the refresh/webhook cross-dedup lookup on `(vehicle_id, signal_code, recorded_at)`.
- `INDEX (vehicle_id, recorded_at DESC)` — history scrolling.

Refresh rows and webhook rows don't duplicate each other ([ADR 0010](adr/0010-on-demand-vehicle-refresh.md)):

- A refresh skips a reading already stored from Smartcar with the same `(vehicle_id, signal_code, recorded_at)`.
- A webhook skips one that a refresh (`poll:` prefix) already stored.

### 3.5a `vehicle_refreshes`

Log of on-demand Smartcar reads (`POST /vehicles/{id}/refresh`, ADR 0010). The per-vehicle rate limit counts these rows. It holds no Smartcar IDs or readings; the readings go to `vehicle_telemetry`.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `vehicle_id` | `uuid` FK → `vehicles.id` ON DELETE CASCADE | |
| `requested_at` | `timestamptz` | When the attempt was recorded, just before calling Smartcar. |
| `outcome` | `text` | `'pending'`, `'ok'`, `'failed'` (`CHECK`). Stays `pending` only if the process died mid-request. |
| `inserted` | `int` | Telemetry rows the refresh added. Default 0. |
| `upstream_status` | `int` | Smartcar's HTTP status when the call failed with a response; otherwise `NULL`. |

Indexes: `INDEX (vehicle_id, requested_at DESC)`.

Retention: rows older than 30 days are deleted for a vehicle whenever a new attempt is recorded for it; the nightly retention job (§6) also prunes vehicles that are never refreshed again. RLS is enabled with no policies, as for the other server-only tables.

### 3.6 `charging_stations`

Cached station records. Treated as a local cache of external data, not the source of truth. Global data with no `user_id`; RLS is enabled like every `public` table. Searches always go to the provider and **upsert** each result on `(provider, external_id)`, so a station's `id` stays the same across fetches and can be referenced by favorites and `planned_stops` ([phase3_plan.md](phase3_plan.md) D7). Nullable columns stay `NULL` when the provider doesn't give a value; nothing is guessed.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | Stable Chargewise ID. |
| `provider` | `text` | `'afdc'`, `'simulated'` (`CHECK`). AFDC includes NRCan's Canadian data, so there is no separate Canadian provider (phase 3 F0). |
| `external_id` | `text` | Provider's station ID. Not null. |
| `name` | `text` | Not null. |
| `operator` | `text` | Nullable. |
| `network` | `text` | Nullable. Provider network code (AFDC `ev_network`). |
| `street_address` | `text` | Nullable. |
| `city` | `text` | Nullable. |
| `region` | `text` | Nullable. State or province. |
| `postal_code` | `text` | Nullable. |
| `country` | `text` | Nullable. ISO 3166-1 alpha-2, e.g. `'US'`, `'CA'` (`CHECK ~ '^[A-Z]{2}$'`). |
| `lat` | `numeric(9,6)` | Not null. `CHECK (BETWEEN -90 AND 90)`. |
| `lon` | `numeric(9,6)` | Not null. `CHECK (BETWEEN -180 AND 180)`. |
| `connectors` | `jsonb` | `[{ type, count, power_kw }]`. `type` is `NACS`, `CCS1`, `J1772` or `CHAdeMO`; `count` and `power_kw` are `null` when the provider doesn't give them per connector (never derived from level totals). Default `[]`. |
| `access` | `text` | `'public'`, `'private'`, `'unknown'` (`CHECK`). Default `'unknown'`. |
| `access_detail` | `text` | Nullable. Provider access restriction detail (AFDC `access_detail_code`), shown as-is. |
| `status` | `text` | `'open'`, `'planned'`, `'temporarily_unavailable'`, `'unknown'` (`CHECK`). Default `'unknown'`. |
| `pricing_text` | `text` | Nullable. Provider pricing text (AFDC `ev_pricing`), shown as-is and never parsed. |
| `source_updated_at` | `timestamptz` | Nullable. Provider's own last-updated timestamp. |
| `fetched_at` | `timestamptz` | When we last fetched the row from the provider; drives the TTL refresh. Default `now()`. |
| `raw_payload` | `jsonb` | Not null. The provider record as received, for auditability and fields we don't map yet. |
| `is_simulated` | `boolean` | Default `false`. `CHECK (is_simulated = (provider = 'simulated'))`. |
| `created_at` | `timestamptz` | Default `now()`. |

Constraints and indexes:
- `UNIQUE (provider, external_id)` — the upsert target.
- `INDEX (lat, lon)` — upgradable to a PostGIS `GIST` index on `geography(Point)` when needed.

### 3.6a `favorite_stations`

A user's starred charging stations ([phase3_plan.md](phase3_plan.md) F8, PRD §4.3). User-owned: every read and write is scoped to the caller (api-contracts §3.19). RLS enabled. Migration `20261119_01`.

| Column | Type | Notes |
|---|---|---|
| `user_id` | `uuid` PK, FK → `profiles.id` | `ON DELETE CASCADE`: deleting the account deletes its favorites. |
| `station_id` | `uuid` PK, FK → `charging_stations.id` | `ON DELETE CASCADE`: if a station leaves the cache, its favorites go too. |
| `created_at` | `timestamptz` | Default `now()`. Returned as `favorited_at`; the list is ordered by it, newest first. |

Constraints and indexes:
- `PRIMARY KEY (user_id, station_id)`. This makes `PUT` idempotent (`ON CONFLICT DO NOTHING`), and its leading `user_id` serves the per-user list.
- `INDEX (station_id)`, so the cascade from `charging_stations` doesn't scan the table.
- At most 500 rows per user, enforced by the API (`FAVORITES_LIMIT`), not the database.

### 3.7 `planned_trips`

A trip the planner produced (Phase 4, [`phase4_plan.md`](phase4_plan.md) F1). `POST /routes/plan` stores **every** result, feasible or infeasible, as an unsaved row (`saved_at` null); `POST /trips/{id}/save` sets `saved_at` (D6). The entire plan payload is stored in `plan_payload` so the UI can re-render without recomputing. Migration `20261118_01`.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | Generated by the planner so `plan_payload.trip_id` matches. |
| `user_id` | `uuid` FK → `profiles.id` ON DELETE CASCADE | |
| `vehicle_id` | `uuid` FK → `vehicles.id` ON DELETE CASCADE | |
| `origin` | `jsonb` | `{ lat, lon, label }`; `label` may be null. |
| `destination` | `jsonb` | `{ lat, lon, label }`. |
| `departure_time` | `timestamptz` NULL | From the request; not used by the v1 planner. |
| `status` | `text` | `'planned'` (default), `'completed'`, `'abandoned'`. CHECK. |
| `plan_status` | `text` | `'feasible'` or `'infeasible'`. CHECK. |
| `plan_payload` | `jsonb` | The full `/routes/plan` 200 body, stored unchanged. |
| `model_version` | `text` | e.g. `'deterministic-v1'`. |
| `is_simulated` | `boolean` | Default `false`. |
| `saved_at` | `timestamptz` NULL | Set once by `POST /trips/{id}/save`; saving again keeps it. Unsaved rows are deleted after 30 days (P6-F5). |
| `created_at` | `timestamptz` | |

Indexes:
- `planned_trips_user_created_idx (user_id, created_at DESC)`: the unsaved list.
- `planned_trips_user_saved_idx (user_id, saved_at DESC, id) WHERE saved_at IS NOT NULL`: the default (saved) list.
- `planned_trips_vehicle_idx (vehicle_id)`: the vehicle → trips cascade and the `vehicle_id` filter.

RLS enabled.

### 3.8 `planned_stops`

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `trip_id` | `uuid` FK → `planned_trips.id` ON DELETE CASCADE | |
| `station_id` | `uuid` FK → `charging_stations.id` ON DELETE SET NULL | Nullable: set to null if the station is evicted from the cache; the stop's details stay in `plan_payload`. |
| `sequence` | `int` | 1-based, route order. CHECK `>= 1`. |
| `arrival_soc` | `numeric(4,3)` | CHECK 0..1. |
| `departure_soc` | `numeric(4,3)` | CHECK 0..1. |
| `charging_minutes` | `int` | The rounded API value (D16). CHECK `>= 0`. |

Indexes: `UNIQUE (trip_id, sequence)`; `planned_stops_station_idx (station_id)` for the SET NULL on station delete.

RLS enabled.

### 3.9 `observed_trips`

One **driving leg** inferred from telemetry ([phase5_plan.md](phase5_plan.md) D1): a stretch of odometer increase with no charging inside it. A road trip with two charging stops is three legs. Written and upserted by trip inference (P5-F3); migration `20261120_01`.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | `gen_random_uuid()`. |
| `user_id` | `uuid` FK → `profiles.id` ON DELETE CASCADE | |
| `vehicle_id` | `uuid` FK → `vehicles.id` ON DELETE CASCADE | |
| `start_time` | `timestamptz` NOT NULL | Earliest possible start: the last at-rest reading before motion. |
| `start_time_latest` | `timestamptz` NOT NULL | First reading showing motion when the start is bounded; equals `start_time` when exact. CHECK `>= start_time`. |
| `end_time` | `timestamptz` NOT NULL | Last reading with an odometer increase. CHECK `>= start_time_latest`. |
| `odometer_start_km` | `numeric(10,2)` NOT NULL | |
| `odometer_end_km` | `numeric(10,2)` NOT NULL | CHECK `> odometer_start_km`. |
| `distance_km` | `numeric(8,2)` NOT NULL | CHECK `> 0` and `= odometer_end_km − odometer_start_km`. |
| `soc_start_percent` | `numeric(5,2)` NULL | CHECK 0..100. |
| `soc_start_recorded_at` | `timestamptz` NULL | |
| `soc_end_percent` | `numeric(5,2)` NULL | CHECK 0..100. |
| `soc_end_recorded_at` | `timestamptz` NULL | |
| `usable_capacity_kwh` | `numeric(6,2)` NULL | Capacity the energy was computed with (D10). |
| `capacity_source` | `text` NULL | `'vehicle'`, `'catalog'`. CHECK: `NULL` iff `usable_capacity_kwh` is `NULL`. |
| `energy_kwh` | `numeric(8,3)` NULL | Observed driving energy, `(soc_start − soc_end) × capacity`. `NULL` when SoC can't give it. No `>= 0` check: a SoC rise within tolerance can make it slightly negative (phase5_plan F2 notes); such legs are `low` and out of aggregates. |
| `energy_kwh_uncertainty` | `numeric(6,3)` NULL | D8. |
| `energy_source` | `text` NULL | `'soc_inferred'`, `'manual'` (reserved). CHECK: `NULL` iff `energy_kwh` is `NULL`. There is no `'odometer_inferred'`: distance × baseline is a prediction, not an observation. |
| `quality_flag` | `text` NOT NULL | `'high'`, `'medium'`, `'low'`. |
| `quality_reasons` | `jsonb` NOT NULL | Array of D8 reason codes. Default `[]`. |
| `review_status` | `text` NOT NULL | `'auto'`, `'needs_review'`, `'confirmed'`, `'rejected'`. Confirmed and rejected legs are frozen: inference never changes or deletes them (D3). |
| `reviewed_at` | `timestamptz` NULL | Set by confirm/reject. |
| `closed` | `boolean` NOT NULL | Default `false`. `false` while the leg may still grow (D14). |
| `planned_trip_id` | `uuid` FK → `planned_trips.id` ON DELETE SET NULL | Set by matching (D4). The leg's position in the plan's chain isn't stored; the API orders the plan's legs by `start_time`. |
| `inference_version` | `text` NOT NULL | `'telemetry-v1'`. |
| `is_simulated` | `boolean` NOT NULL | Default `false`. Copied from the vehicle. |
| `created_at`, `updated_at` | `timestamptz` NOT NULL | Default `now()`. `updated_at` is set by the ORM on update; a bulk `UPDATE` or upsert must set it itself. |

Indexes: `UNIQUE (vehicle_id, odometer_start_km)` (the upsert key); `(user_id, end_time DESC, id)` for lists and analytics; `(vehicle_id, end_time DESC)`; `(planned_trip_id) WHERE planned_trip_id IS NOT NULL` for matching and the SET NULL on plan delete.

RLS enabled.

### 3.10 `prediction_results`

Pairs a prediction with what happened, so analytics can compute error. Two kinds of row: `'plan'` scores a matched plan against its chain of legs (D4); `'leg'` is a backtest of the baseline model against one finished leg with energy (D9).

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | `gen_random_uuid()`. |
| `user_id` | `uuid` FK → `profiles.id` ON DELETE CASCADE | Ownership filter without a join. |
| `vehicle_id` | `uuid` FK → `vehicles.id` ON DELETE CASCADE | |
| `kind` | `text` NOT NULL | `'plan'`, `'leg'`. |
| `planned_trip_id` | `uuid` FK → `planned_trips.id` ON DELETE CASCADE, NULL | CHECK: set iff `kind = 'plan'`. |
| `observed_trip_id` | `uuid` FK → `observed_trips.id` ON DELETE CASCADE, NULL | CHECK: set iff `kind = 'leg'`. Plan rows reach their legs through `observed_trips.planned_trip_id`. |
| `model_version` | `text` NOT NULL | `'deterministic-v1'`. |
| `distance_km` | `numeric(8,2)` NOT NULL | Distance the prediction is for: plan route + detours, or the leg's odometer distance. |
| `observed_distance_km` | `numeric(8,2)` NOT NULL | Leg distance, or the chain's sum. |
| `predicted_energy_kwh` | `numeric(8,3)` NOT NULL | |
| `observed_energy_kwh` | `numeric(8,3)` NULL | `NULL` when any leg lacks energy. |
| `error_kwh` | `numeric(8,3)` NULL | `observed − predicted`. |
| `predicted_arrival_soc`, `observed_arrival_soc` | `numeric(4,3)` NULL | Plan rows only. CHECK 0..1. |
| `observed_start_soc` | `numeric(4,3)` NULL | Plan rows only. CHECK 0..1. |
| `arrival_soc_error_points` | `numeric(5,2)` NULL | `(observed − predicted) × 100`. Plan rows only. |
| `inputs` | `jsonb` NOT NULL | `{baseline_kwh_per_km, baseline_source, usable_capacity_kwh}` (leg rows) or `{plan_model_version}` (plan rows). |
| `is_simulated` | `boolean` NOT NULL | Default `false`. |
| `created_at`, `updated_at` | `timestamptz` NOT NULL | Default `now()`; `updated_at` as in §3.9. |

Indexes: `UNIQUE (planned_trip_id, model_version)` and `UNIQUE (observed_trip_id, model_version)`: one row per plan or leg per model version. They are plain unique constraints rather than partial indexes `WHERE kind = …`: the kind ↔ FK checks make them equivalent (`NULL`s never collide), `ON CONFLICT` needs no index predicate, and the FK cascades use them. Also `(user_id, kind, created_at DESC)`, `(model_version, created_at)` and `(vehicle_id)` for the vehicle cascade.

RLS enabled.

**Retention (P6-F5):** only unsaved, unmatched plans expire (`saved_at IS NULL AND status = 'planned'`), so matched plans and their `'plan'` rows are kept.

### 3.11 `consent_records`

Append-only audit of a user's answers to the privacy notice (PRD §4.6 "consent state is stored and auditable", P6-F5). A change is a new row, never an update; the latest row per `(user_id, kind)` is the current answer (api §3.1c).

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | `gen_random_uuid()`. |
| `user_id` | `uuid` FK → `profiles.id` ON DELETE CASCADE NOT NULL | Deleted with the account. |
| `kind` | `text` NOT NULL | `'privacy_notice'` (`CHECK`). New kinds need a migration. |
| `version` | `text` NOT NULL | The notice version answered (`PRIVACY_NOTICE_VERSION`). 1–32 chars (`CHECK`). |
| `granted` | `boolean` NOT NULL | `true` accepted, `false` declined or withdrawn. |
| `recorded_at` | `timestamptz` NOT NULL | Default `now()`. |
| `source` | `text` NOT NULL | `'web'` (`CHECK`). |

Indexes: `(user_id, kind, recorded_at DESC)`. RLS enabled with no policies.

### 3.12 `account_deletions`

One row per deleted account (P6-F5, api §3.1b). Written in the same transaction that deletes the profile; **no foreign key**, so it survives the cascade.

| Column | Type | Notes |
|---|---|---|
| `user_id` | `uuid` PK | The deleted Supabase user ID. Links to nothing once the auth user is gone. |
| `requested_at` | `timestamptz` NOT NULL | Default `now()`. |
| `auth_user_deleted_at` | `timestamptz` NULL | Set once Supabase confirms the auth-user deletion (or answers 404). `NULL` = still owed. |
| `pending_smartcar_connection_ids` | `jsonb` NOT NULL | Array (`CHECK`) of Smartcar connection IDs whose revocation failed. Default `[]`. The only Smartcar identifiers kept after deletion, and only until revoked. |
| `attempts` | `int` NOT NULL | Retention-job retries. Default 0. |
| `last_attempt_at` | `timestamptz` NULL | |

What it is for:

- **No resurrection.** `get_or_create_profile` refuses a user with a row here (`401`), so a Supabase access token that is still valid can't lazily recreate the profile through `/me`, Connect, the planner or favorites.
- **Owed work.** The retention job retries the revocations (until `PRIVACY_REVOCATION_GIVE_UP_DAYS`, 30) and the auth-user deletion (until it succeeds).
- **Removal.** The job deletes the row once nothing is owed and `auth_user_deleted_at` is older than `PRIVACY_TOMBSTONE_DAYS` (7), which must stay longer than the Supabase JWT expiry. The age counts from the auth-user deletion, not from `requested_at`: until then the user can still refresh tokens, so a token issued just before the deletion stays valid for one more token lifetime.

RLS enabled with no policies.

## 4. Provenance and unit discipline

- `source`, `recorded_at`, `received_at` live on every externally derived row.
- `vehicle_telemetry.raw_payload` keeps the normalized signal entry even after it has been projected into typed columns, so that a later schema migration can re-derive values without round-tripping to Smartcar.
- Units are stored raw. The API layer exposes units in field names (`range_km`, `odometer_km`); the frontend converts for display.

## 5. Simulated vs real data

The public demo depends on being able to seed convincing plans without touching real vehicles. Rules:

- Seeded rows land in the same tables with `is_simulated = true`.
- All default analytics, ML training, and `/api/v1/analytics/consumption` queries filter `is_simulated = false`.
- The seed script lives in `services/api/scripts/seed_demo.py` (to be created in Phase 6) and must never run against a database that contains real telemetry.

## 6. Location and privacy

- Location columns (`vehicles.latest_state.location`, `charging_stations.lat/lon`; `observed_trips` has no location columns, phase5_plan D7) are classified sensitive.
- Account deletion (`DELETE /api/v1/me`, api §3.1b) removes `profiles`, which cascades in the database to `user_preferences`, `consent_records`, `favorite_stations`, `vehicles` and through them `vehicle_specs` (incl. the per-vehicle baseline), `vehicle_telemetry`, `vehicle_refreshes`, `planned_trips`, `planned_stops`, `observed_trips` and `prediction_results`. Nothing is anonymized and kept: every row is deleted. `tests/privacy/test_account_deletion.py` checks from the Postgres catalog that every table with a `user_id`, and every table reachable from `profiles`, is on this list.
- Retained after deletion: the `account_deletions` tombstone (§3.12; the user ID and any unrevoked Smartcar connection IDs, removed by the retention job), and `charging_stations`, which is global cache data.
- Before the profile is deleted, the user's Smartcar connections are revoked and the vehicle rows locked. A webhook that arrives later finds no vehicle and is dropped; post-ingest hooks and refreshes for the deleted vehicle write nothing.
- **Retention job** (`services/api/scripts/retention.py`, run nightly; `--dry-run` counts only). It deletes:
  - unsaved, unmatched plans after 30 days (`PRIVACY_UNSAVED_TRIP_DAYS`);
  - `vehicle_telemetry` whose provider `recorded_at` is older than 24 months (`PRIVACY_TELEMETRY_RETENTION_DAYS`, 730), in batches per vehicle;
  - `vehicle_refreshes` older than 30 days (`PRIVACY_REFRESH_LOG_DAYS`).
  It then works through the deletion backlog (§3.12). The windows are server-wide; per-user retention isn't built.
- No raw lat/lon is included in Sentry breadcrumbs or logs. Coordinates are rounded to 2 decimal places in log output.

## 7. Migration policy

- Every schema change is a reviewed Alembic migration. No ad-hoc SQL in production.
- Migrations must be reversible, or explicitly document why they are not.
- CI runs `alembic upgrade head && alembic downgrade -1 && alembic upgrade head` against a disposable Postgres.
- Breaking column changes follow expand/contract: add the new column, backfill, switch readers, switch writers, drop the old column in a later migration.

## 8. When to add PostGIS

Not in the MVP. Adopt PostGIS when the first query that actually benefits from it appears — likely "find chargers within X km of a route polyline" if we start caching routes. Until then, provider APIs handle proximity.
